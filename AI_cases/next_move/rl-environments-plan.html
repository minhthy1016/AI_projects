RL environments for MCP-driven software engineering

Reproducible, SWE-bench-style environments that test whether an agent can fix, extend, refactor and speed up a real financial-filings pipeline, when the information it needs can only be found through MCP tools.

Blockers to fix first

  • The code depends on the Fabrion venv for Docling and lxml.
  • data/ is 935 MB and mostly gitignored, so we need a small frozen fixture bundle.
  • data/gold/ is committed to git, so the answers would sit on disk where the agent can read them. It must be removed from the agent image.
  • The Python version (3.14 in __pycache__) needs pinning inside the image.

Core rule

The information needed to solve each task can only be found through MCP tools. The repo and visible tests are never enough.

Example: fixing OMV's profit_after_tax identity requires finding ProfitLossFromDiscontinuedOperations through the XBRL MCP server. It is not in the repo.

Every task is checked by running it with MCP access removed. The solve rate should fall to about 0. If it doesn't, the task isn't testing MCP use and gets rewritten. Scoring stays deterministic: the grader decides, and tool-call traces are for diagnosis only, not reward.

Models & scoring

A deterministic resolve rate decides pass or fail. The LLM judge adds separate scores next to it and never overrides it.

Planner
Claude Sonnet 4.5

Reads the issue, plans the MCP discovery and the fix. Scored on plan quality (judge, advisory).

Executor
gpt-oss-120b

Edits code and runs tests. Scored on resolve rate. Turn budget 80–100.

Judge
Larger model

Scores trace quality, whether MCP use was sensible and whether the plan was followed. Advisory only.

Every task runs in three setups

A
gpt-oss-120b alone
B
Sonnet 4.5 alone
C
Sonnet plans → gpt-oss executes

The difference between C and A is the value of planning. The difference between runs with and without MCP is the value of MCP use. Both are reported alongside the resolve rate.

Decide early

  • Keep the judge separate from the planner. If Sonnet writes the plan and a Claude model also judges it, the judge tends to favour its own style. Use a different model family, or check the judge against about 30 traces labelled by hand before trusting it.
  • Pin exact model IDs for every run. Newer models exist (Sonnet 5 is current), so the model ID string must be fixed for results to be reproducible.
  • Run each setup at least 3 times. One run is not evidence. Earlier dbt experiments showed the same model swinging between results depending on the environment.

Task format

SWE-bench instance fields, plus three extra fields for MCP and anti-cheating.

# SWE-bench fields
instance_id  repo  base_commit  problem_statement
patch  test_patch  FAIL_TO_PASS  PASS_TO_PASS

# extra fields
mcp_servers            # which servers are mounted for this task
mcp_required_evidence  # facts only reachable via MCP (for the no-MCP check)
heldout_variant        # hidden test on a different company / period

# on disk
task/
  task.yaml        repo commit, image digest, MCP manifest, prompt, family, difficulty
  hidden_tests/    fail-to-pass + pass-to-pass, never mounted for the agent
  golden.patch     reference solution
  golden_trace     reference MCP call sequence (documentation, not grading)
  verify.sh        tests → pipeline output vs answers → contract check

Resolve rate = the share of task runs where every fail-to-pass and pass-to-pass test passes. Failed and incompatible runs count as 0. The full scorecard is in Scoring.

Scoring

Adapted from micro1 LongExtractionBench: 225 documents averaging 358 pages each, scored by a deterministic grader. We copy its structure and fix its two weak points.

Keep "does it finish" separate from "is it right when it finishes."

Their leaderboard shows why: precision is between 80% and 99.6% for every system, while recall ranges from 34% to 99.6%. AI_cases shows the same pattern: precision is 100% but filing coverage is only 11.6–44%. A patch that simply outputs fewer facts keeps precision perfect, so recall must always be scored.

Accuracy metrics

These apply to tasks whose result is a set of extracted facts. Facts are matched by key, never by row position. Each truth fact can be matched at most once, so duplicates count as extras.

# matching key
key = (entity_LEI, concept, period_start, period_end, unit, dimensions)

# Pred  = facts the agent's pipeline outputs, inside the task scope
# Truth = XBRL facts inside the task scope (fixed by the task author, hidden)
# M     = keys found in both

fact precision       = |M| / |Pred|        # penalises made-up, duplicated and extra facts
fact recall          = |M| / |Truth|       # penalises missed facts
value accuracy       = correct(M) / |M|    # value correct, given the key matched
correct-fact recall  = correct(M) / |Truth| # = recall × value accuracy

# value is correct when:
round(value × scale, decimals) == round(truth_value, decimals)
# with decimals taken from the filing's declared precision (XBRL decimals)
  • Correct-fact recall is the single accuracy number to report first. Value accuracy alone shares LongExtractionBench's weakness: it is measured only on facts that matched, so an agent that returns fewer, easier facts scores well on it.
  • The normaliser only fixes how a number is written. It handles whitespace, thousands separators and decimal separators. It must not fix sign, scale or period, because those are exactly the bugs the tasks test (for example the Repsol sign convention). A normaliser that fixed them would give credit for the bug.
  • The recall scope is set by the task, not by the agent. AI_cases' own recall_inscope uses "labels the agent declared" as the denominator, which rewards declaring fewer. In the environment, the scope is part of the hidden task definition.
  • Verifiability is reported next to precision. Some facts can't be checked because the company didn't tag them in XBRL. Reporting how many can't be checked stops a result from looking better by leaving them out, as trust = precision × verifiability already does in AI_cases.

Three views of every result

Unconditional
Failures count as 0. This is the headline number.
Conditional
Finished runs only, as LongExtractionBench reports.
Common subset
Only tasks every compared setup finished. The only fair head-to-head view.

Why the conditional view alone misleads: on LongExtractionBench, Claude Opus 4.8 scored 92% precision on the 116 documents it finished, averaging 86 pages, while Reducto scored 99.6% on all 225, averaging 367 pages. Those numbers come from different documents and can't be compared directly.

Where our answer data is stronger

  • LongExtractionBench's answer labels were drafted by GPT-5.5 and Claude Opus 4.7, and humans only settled disagreements. Where both models made the same mistake, the answer data inherits it. Our answer data is XBRL filed by the companies themselves; no model produced it.
  • They release only 50 of their 225 documents, and the sponsor came first. We should publish a public task split and keep a held-out split, and state which one each reported number comes from.

Guarding against reward hacking

  • Hidden tests run on a different company or period than the one in the prompt, so hard-coded answers fail.
  • tests/ and contracts/ are hashed to detect tampering.
  • Gold data is removed from the image.
  • Every task must fail three negative controls: a no-op patch, deleting the tests, and a hard-coded answer.

Quality gate

Quality per task over volume. A task counts only when it passes every item below.

  • golden passesThe golden patch resolves the task from a clean image.
  • controls failNo-op, test-deletion and hard-coded patches all fail.
  • held-out variantA hidden test on a different company or period.
  • MCP necessitySolve rate falls to about 0 without MCP access.
  • n ≥ 3At least 3 runs per model setup.
  • reproducibleTwo clean runs give identical verify results.
  • human reviewReviewed by hand, especially tasks at 0% or 100%.
  • difficulty bandSolve rate between 10% and 70% across setups.

3-month timeline

Month 1 · Sep 22 – Oct 19

One complete working slice

  • Remove the Fabrion dependency; pin Python; freeze a git snapshot of AI_cases.
  • Build the fixture bundle (8 companies, statement pages only, pre-parsed JSON, about 50 MB) and the Docker image, with gold data removed.
  • Set up xbrl-facts, Docling MCP, Filesystem MCP and the logging proxy.
  • Adopt the SWE-bench harness. Write 5 pilot tasks with golden patches.
  • Run setups A, B and C, 3 times each, plus the no-MCP check.
Exit5 tasks pass the full quality gate.
Month 2 · Oct 20 – Nov 16

More servers, more tasks

  • Add Gitea + gitea-mcp, Git MCP and DuckDB MCP.
  • Adapt SWE-smith for bug injection: reverse a fix, keep it only if one of the 195 tests flips from pass to fail, then wrap it into a task.
  • Bring in the LLM judge and check it against about 30 hand-labelled traces.
  • Add 3–5 tasks on Arelle or edgartools.
ExitAbout 15 validated tasks; judge agreement with human labels measured.
Month 3 · Nov 17 – Dec 20

Calibrate, add page-image parsing, write up

  • Calibrate difficulty with pass@k. Keep tasks in the 10–70% band; review every 0% task by hand.
  • Add page-vision on vLLM, with each page's VLM output cached and frozen per model version. Build tasks that run the same bug on the Docling parse and the VLM parse.
  • Build a leaderboard of the three setups, including the planning gain and the no-MCP results.
  • Write the POC documentation.
Exit20–25 validated tasks, leaderboard and write-up.
